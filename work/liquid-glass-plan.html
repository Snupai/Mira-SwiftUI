Mira: native macOS UI and Liquid Glass

Modernize navigation, toolbars, search, and sheet chrome using standard SwiftUI components. Let macOS supply its adaptive materials, preserve custom themes intentionally, and add custom glass only where an app-specific control needs it.

Implementation result · October 8, 2026

Scope and starting point

Mira is a SwiftPM macOS app targeting macOS 14. The inspected checkout uses a fixed-width custom sidebar in Sources/Mira/App/ContentView.swift, custom headers and search fields in invoice/client lists, opaque theme fills, and a hidden window title bar in Sources/Mira/App/MiraApp.swift.

This plan covers the main shell, invoice/client navigation controls, and material conflicts in presented editors and Settings. Keep invoice calculations, PDF rendering, persistence, encryption, CloudKit, release metadata, and roadmap features outside this UI change.

Source inspection established these targets; runtime appearance and SDK availability still require validation.

1. Establish the compatibility and visual baseline

  • Read applicable repository instructions and the Liquid Glass skill. Use the build-run-debug skill for app launch and runtime checks.
  • Verify installed Xcode, Swift, SDK, and macOS versions. Explicit Liquid Glass APIs require the macOS 26 SDK; guard their use with availability checks and keep the deployment target at macOS 14.
  • Build and launch a foreground .app bundle using the repository's bundle workflow. Use disposable test data or a separate test account so UI validation cannot migrate or edit personal invoice data.
  • Capture baseline screenshots of all sidebar destinations, invoice/client search, editor sheets, and Settings in Default and Catppuccin themes, light and dark.
  • Record existing keyboard shortcuts, section selection, search/filter behavior, and sheet entry points before changing structure.

Done when: the current app runs as a foreground bundle and the validation environments and baseline behaviors are recorded.

2. Replace the custom sidebar with native navigation

Primary files: Sources/Mira/App/ContentView.swift and Sources/Mira/App/MiraApp.swift.

  • Replace the macOS HStack sidebar with NavigationSplitView and a selectable native sidebar List using Label rows.
  • Keep Dashboard, Invoices, Clients, and Settings destinations and the initial Invoices selection. Preserve notification-driven navigation, new-item commands, and existing sheets.
  • Let the sidebar resize/collapse using system behavior. Remove fixed-width sidebar styling, opaque sidebar fills, and custom selection/button chrome.
  • Assess the hidden-title-bar window style with the new toolbar; choose the native title/toolbar configuration that keeps traffic lights, title, and actions coherent.
  • Retain each section's search/filter state when navigating away and back. Move state ownership only where required to prevent resets.

Done when: all sections, keyboard navigation, sidebar toggling/resizing, and editor presentation work through the native shell.

3. Move invoice and client actions into native toolbars

Primary files: Sources/Mira/Views/Invoices/InvoiceListView.swift and Sources/Mira/Views/Clients/ClientListView.swift.

  • Replace hand-built page action headers with navigation titles and native toolbar items. Keep list content and invoice status filters in the content area unless moving them clearly improves usability.
  • Use standard labeled buttons for New Invoice and New Client, with accessible names and existing actions. Remove custom colored rectangles and plain-button chrome from these toolbar actions.
  • Keep invoice sorting in a standard Menu. Group related actions with native toolbar placement; use ToolbarSpacer on supported systems only when a distinct group is useful.
  • Use monochrome icons by default and semantic tint for primary actions/status. Apply badges or shared-background visibility only where an actual product requirement calls for them.
  • Confirm toolbar items do not duplicate shell commands or disappear when switching sections or narrowing the window.

Done when: new-item actions and sorting remain discoverable and accessible in the system toolbar, with coherent grouping on macOS 26 and usable fallback layouts on macOS 14.

4. Adopt native search with explicit scope

  • Replace invoice/client custom search fields with .searchable, preserving existing matching rules, placeholder text, and independent search state.
  • Keep search scoped to the active invoice or client destination. Do not imply global search across Dashboard and Settings.
  • Attach search to the destination/container that produces the correct toolbar placement. If scope later becomes global, move it to NavigationSplitView and define cross-section results first.
  • Consider searchToolbarBehavior on supported systems only if compact secondary search is appropriate. Preserve search access through keyboard and pointer interaction.
  • Check search combined with status filtering, sorting, clearing, empty results, and section switching.

Done when: native search filters the same records as before and its placement and scope are clear.

5. Reconcile themes, sheets, and custom surfaces

Primary files: Sources/Mira/Services/ThemeManager.swift, Sources/Mira/Models/AppTheme.swift, Sources/Mira/Views/Settings/SettingsView.swift, Sources/Mira/Views/Invoices/InvoiceEditorView.swift, and the client editor in Sources/Mira/Views/Clients/ClientListView.swift.

  • Use native materials for navigation chrome in every theme. Preserve theme palettes for document/content surfaces and user-selected accents; do not rewrite imported theme JSON or alter PDF brand colors.
  • Remove opaque root/sidebar/toolbar and sheet fills where they obstruct system material. Audit nested backgrounds and clipping before deciding a glass effect is missing.
  • Keep purposeful content-card and field backgrounds where they help readability. Check Default, Catppuccin, and a custom imported theme for text contrast.
  • Use standard controls first. Add availability-guarded glass or glass-prominent button styles only where appropriate, with conventional native styles on older systems.
  • Only add glassEffect if a remaining app-specific floating control justifies it. Group nearby custom glass in a single GlassEffectContainer, use interactive glass for controls, and use stable IDs plus a local namespace if morphing is needed.
  • Evaluate scroll-edge treatment with system defaults first. Add availability-guarded scrollEdgeEffectStyle only if dense content requires tuning. Skip background extension and zoom transitions unless the design actually benefits from them.

Done when: system chrome renders without conflicting fills, theme content remains readable, and no unnecessary custom glass layer is introduced.

If the native shell provides the desired glass treatment, complete the work without introducing custom glass surfaces.
